- Implementato `src/parsing.py`:
  - Conversione PDF → JSON strutturato tramite Docling

- Analizzata e implementata architettura di retrieval a 2 stadi in `src/retrieval.py`: Bi-Encoder (ChromaDB) + Cross-Encoder Re-ranker (`BAAI/bge-reranker-v2-m3`)
- Individuato e risolto bug di duplicazione dati nel DB vettoriale (stessi file in più cartelle TOPIC)
- Analizzati punteggi Cross-Encoder e identificato rumore da tag HTML residui di Docling nei chunk
- Sviluppato `src/generation.py` con client OpenAI-compatible puntato all'API locale Ollama (`http://localhost:11434`)
- Implementato `compare.py`: A/B testing automatico RAG vs Baseline (LLM puro senza retrieval), avviabile con `python compare.py`
- Ottimizzata "Instruction Hierarchy" nel System Prompt con blocco "Fail-fast": se il contesto non contiene la risposta, il modello risponde con messaggio fisso invece di allucinare

- Implementato `main.py`: CLI interattiva per testare il sistema RAG completo (`python main.py`)

### Decisioni prese
| Decisione | Motivazione |
|-----------|-------------|
| Embedding: `BAAI/bge-m3` | Allinea semanticamente IT e EN nello stesso spazio vettoriale — no pipeline di traduzione separata |
| Vector store: ChromaDB locale persistente (`data/vector_db/`) | No dipendenze cloud, sviluppo rapido, API semplice |
| Parser PDF: Docling (`do_formula_enrichment=True`, `do_ocr=True`) | Estrazione accurata di formule LaTeX, tabelle e layout complessi |
| Naming convention PDF: `[LIVELLO(i)] - [Titolo].pdf` | Permette estrazione automatica del livello via regex in `parsing.py` |
| Organizzazione dati: cartelle `TOPIC N - [Nome]/` in `data/raw/` | Metadata topic estratti automaticamente dal nome cartella |
| Elaborazione PDF a blocchi di 10 pagine + `gc.collect()` | RTX 3050 Ti con 4 GB VRAM — necessario per evitare crash da `std::bad_alloc` |
| ID chunk = `MD5(testo)` invece del nome file | Testi identici in topic diversi vengono unificati in un solo vettore via `upsert` |
| Nessun filtro per Topic nel retrieval | Permette collegamenti semantici trasversali (serendipità semantica); unico filtro stringente: `difficulty_level` |
| Retrieval a 2 stadi: Bi-Encoder + Cross-Encoder | Massimizza precisione e riduce allucinazioni: ricerca grezza → re-ranking semantico |
| LLM: `qwen2.5:3b` via Ollama | Taglia ridotta (~2.2 GB), ottima padronanza italiano, alta aderenza alle istruzioni di sistema |
| Embedding + reranker forzati su CPU | 4 GB VRAM dedicati interamente a Ollama per la generazione testuale |
| DPO rinviato al cloud (Kaggle/Colab) | Impossibile eseguire fine-tuning in locale con 4 GB VRAM |
| `max_tokens` disattivato | Permette spiegazioni universitarie lunghe senza troncature |
| `frequency_penalty=0.6`, `presence_penalty=0.5` | Previene loop tipici dei modelli 3B pur permettendo ripetizione di variabili nelle equazioni |
| Query Expansion IT↔EN in `generation.py` | Garantisce retrieval corretto di formule scritte in lingua diversa dalla query |

### Problemi e soluzioni
| Problema | Stato | Soluzione / Note |
|----------|-------|------------------|
| OOM / `std::bad_alloc` durante il parsing di PDF lunghi | ✅ Risolto | Elaborazione a blocchi (`page_range`) di 10 pagine + `gc.collect()` dopo ogni blocco |
| Duplicati nel DB vettoriale da file presenti in più cartelle TOPIC | ✅ Risolto | Deduplicazione via MD5 del testo + `upsert` in ChromaDB |
| Bias linguistico: query in IT non trova formule scritte in EN (e viceversa) | ✅ Risolto | Query Expansion: `generation.py` traduce la query prima di passarla al retriever |
| Rumore Cross-Encoder da tag HTML residui di Docling nei chunk | 🔄 Aperto | Da risolvere aggiungendo regex di pulizia in `src/chuncking.py` |
